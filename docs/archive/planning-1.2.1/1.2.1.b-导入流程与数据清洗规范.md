# 3.b 股权全景结构化：导入流程与数据清洗规范

## 范围
- 定义从“网页导出/下载表格”到“标准 CSV”再到“Postgres 入库”的可执行流程与可验收产物。
- 本规划强调**半自动导出 + 可追溯清洗**，避免合规与风控风险。

## 交付物
- 目录规范：`raw/`、`normalized/`、`conflicts/`、`logs/`。
- 标准化输出：`normalized/entities.csv`、`normalized/equity_edges.csv`、（可选）`normalized/targets.csv`。
- 可复现的导入顺序与最小 QA 清单（导入完成后立刻可验收）。

## 0) 目录与命名规范（建议）
- `raw/`：原始导出文件（建议每家公司一个子目录）
- `normalized/`：清洗后的标准 CSV
- `conflicts/`：同名消歧、信用代码冲突、无法关联的边等异常清单
- `logs/`：导入日志（含时间、批次、失败原因）

## 1) 每家公司最小导出包（网页导出）
以“能构建股权图”为最小目标，建议每家公司至少拿到：
- 企业基本信息（含统一信用代码、地区、行业、状态）
- 股东信息/股东及出资（含持股比例或原始文本）
- 对外投资（用于下游补充口径）
- 实控人/最终受益人（如平台提供，用于上游终点类型标注）

## 2) 标准化与消歧策略
### 主体去重优先级
1. `credit_code` 一致 → 同一主体
2. 信用代码缺失时：`name + province/city + established_date` 候选匹配
3. 仍无法判断 → 输出到 `conflicts/`，人工复核并记录结论

### 股权边规范化
- `hold_pct`：尽量解析为 0~100 数值；解析失败/区间/未知写入 `hold_pct_text`
- 同一 `from -> to` 多条：
  - 若一致可去重
  - 若不一致：保留并标注来源（`source_platform/source_doc/collected_at`）

## 3) 下游阈值 20% 的落地方式
口径：下游纳入递归：持股比例 ≥ 20%（`min_pct=0.2`）。

建议做法（本期执行标准）：
- 入库 **保留全部可得边**
- 图谱展开与统计时通过查询参数 `min_pct` 控制“递归范围”
- 好处：未来调整阈值（10%/30%）无需重导入

## 4) 入库步骤（逻辑顺序）
1. 创建一个 `snapshot_name`（例：`2026-04-08_run1`），后续所有 CSV 行都写入该批次
2. 导入 `entities.csv` → `entities`
   - 先插入主体，再生成/回填内部 `entity_id`
   - 对 `credit_code` 唯一约束冲突的行：转入 `conflicts/` 复核
3. 导入 `targets.csv`（30 家目标） → `company_targets`
   - 用 `credit_code` 或 `name` 关联到 `entities.entity_id`
4. 导入 `equity_edges.csv` → `equity_edges`
   - 将 `from_*`、`to_*` 解析/关联为内部 `entity_id`

## 5) 最小 QA（导入后必须立刻可验收）
- 覆盖率：30 家目标公司是否都能匹配到 `entity_id`（或明确缺失原因）
- 边完整性：每条边 from/to 是否都能匹配到主体（否则输出到 `conflicts/unresolved_edges.csv`）
- 比例异常：`hold_pct < 0`、`hold_pct > 100`、`hold_pct` 为空且 `hold_pct_text` 也为空
- 重复边：同一批次同一对主体大量重复（确认是多来源还是解析重复）

## 6) 输出（给后端/前端用）
- 后端按 [`3.c`](规划/3.c_3.0-后端API契约与查询参数.md) 输出 `nodes/edges` JSON
- 前端按 [`3.d`](规划/3.d_3.0-前端页面与图谱组件契约.md) 渲染图谱与页面
- QA 按 [`3.e`](规划/3.e_3.0-QA与验收标准.md) 做一致性与异常校验

## 风险与依赖
- 依赖 [`3.a`](规划/3.a_3.0-数据契约与字段字典.md) 的字段字典稳定，否则清洗与入库会出现“字段漂移”导致返工。
- 消歧依赖人工复核的吞吐，需要在排期中预留（尤其是信用代码缺失较多时）。
