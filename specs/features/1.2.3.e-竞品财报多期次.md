## 1. 背景与目标

### 1.1 现状（1.2.3.c）

- 横向汇析：**全局单例** `{upload_dir}/competitor/report.snapshot.json`；上传即覆盖。
- 展示：侧栏 → `/competitor`；纵向 → `/competitor/vertical`（PDF 优先）。
- 内容期次实质为 **2025 年报** 一份蓝本。

### 1.2 目标（1.2.3.e）

1. 支持多份 **edition（期次）** 并存（至少：`2025-annual`、`2026-h1`），互不覆盖。
2. 侧栏「竞品财报」进入 **current edition**（通常为最新半年报/年报）。
3. **2025 年报页面与数据保留**，经页内期次切换可访问（深链可分享）。
4. 半年报横向蓝本允许 **部分 sec / 子锚点细节变化**（如理财明细）；解析与前端按锚点降级，不要求与年报表结构逐列一致。
5. 纵向汇析可按期次关闭：`has_vertical=false` 时隐藏纵向入口（预期 **2026-h1 关闭**；**2025-annual 可保留**既有纵向数据与入口）。
6. 财务后台改为 **期次列表 + 指定期次上传 + 设置 current**，禁止无 edition 的盲目覆盖。

### 1.3 非目标

- 不在一份 Snapshot 内用「多年份宽表」混存多期。
- 不做侧栏多级历史菜单（方案 B）；不做永久双入口占满侧栏（方案 C）。
- 不自动从 KB PDF 生成半年报 MD。
- 不把 Agent/KB「竞品财报25」文件夹与 edition 强绑定（可二期对齐标签）。
- 不在本特性内重做各 sec 图表（仅适配缺表/新表空态；细节图表迭代可另开任务并回写本 spec）。

### 1.4 与 1.2.3.c 的关系

- **1.2.3.c** 仍是「单期横向仪表盘」能力基线（九屏、解析器、RBAC）。
- **1.2.3.e** 在其上增加 **多期次存储、current 指针、展示切换、后台期次管理、纵向按期开关**。
- 迁移后，1.2.3.c 文档中「全局单例」表述视为被本特性 **supersede**；1.2.3.c 正文应加指向本文件的链接（见 §13）。

## 2. 入口方案 A（已选定）

| 项 | 约定 |
|----|------|
| 侧栏 | 仍一个「竞品财报」图标/文案；点击 → `/competitor` = **current** |
| 默认数据 | `GET /api/competitor/report` 无参 = current edition |
| 历史访问 | 页头 **期次切换** → `/competitor/e/{edition_id}`（推荐）或兼容 `?edition=` |
| 深链 | 分享 `/competitor/e/2025-annual` 应稳定打开 2025 年报 |
| 纵向 | 仅当 **当前选中期次** `has_vertical=true` 时展示入口；否则隐藏或点进友好空态 |

```text
侧栏[竞品财报] ──► /competitor          （current，如 2026-h1）
页头[期次▾]   ──► /competitor/e/2025-annual
                 └─ 若 has_vertical → 可进 /competitor/vertical?edition=2025-annual
```

## 3. 数据模型

### 3.1 Edition

```typescript
type CompetitorEditionKind = "annual" | "interim";

type CompetitorEditionMeta = {
  edition_id: string;          // 稳定 id，如 "2025-annual" | "2026-h1"
  kind: CompetitorEditionKind;
  period_label: string;        // UI：「2025 年报」「2026 半年报」
  has_vertical: boolean;
  /** 可选：本期强调的锚点差异说明，供后台诊断 */
  notes?: string;
  uploaded_at?: string;
  uploaded_by?: string;
  source_filename?: string;
  title?: string;
  company_count?: number;
};
```

### 3.2 磁盘布局

```text
{upload_dir}/competitor/
  current.json                 # { "edition_id": "2026-h1" }
  editions/
    2025-annual/
      meta.json
      report.md
      report.snapshot.json
      history/…                # 可选，同 1.2.3.c
      vertical/…               # 可选；has_vertical=true 时使用
        # 复用既有 vertical.snapshot / pdfs 迁入本目录
    2026-h1/
      meta.json
      report.md
      report.snapshot.json
      # 通常无 vertical/
```

**迁移（一次性）：**

1. 若存在旧单例 `report.snapshot.json` / `report.md`，迁入 `editions/2025-annual/`。
2. 若存在旧 `vertical*` / `vertical/pdfs`，迁入 `editions/2025-annual/vertical/`（或等价路径，实现时固定一种并写清 store API）。
3. 写 `current.json` → 初始可仍为 `2025-annual`；上传并验收 `2026-h1` 后由管理员设为 current。
4. 旧根路径文件：迁移成功后可保留只读副本一版或删除；**禁止**新上传再写回根路径单例（兼容读一层后废弃）。

### 3.3 Snapshot

- 继续使用 1.2.3.c 的 `CompetitorReportSnapshot`（`version: 1`）。
- `meta` 建议增加（解析或上传时写入）：`edition_id`、`kind`、`period_label`（与 `CompetitorEditionMeta` 对齐）；旧 snapshot 缺省时由目录 `meta.json` / edition_id 补齐。

### 3.4 半年报 sec 差异

- 蓝本仍是 **整份 MD 一期一份**（禁止半文件 patch 合并）。
- 解析器保持锚点驱动；缺表/新表 → `warnings`，不阻断（除非缺主章节 `sec-01`～`sec-09` 的既有硬规则需按半年报放宽——**若放宽须先改本 spec 再改 parser**）。
- 前端：按 `getTable(anchor)` 取数；无表则该模块空态，不因缺「理财明细」旧表崩溃。
- **sec-09-7 投资理财**：宽表（科目 × 公司）为汇总；同锚点另有一张表（通常是「公司 + 金额」长表）时，按政府补助明细展示表 + 分项合计柱。只有汇总表时不渲染明细占位。
- **sec-06-a**：货币资金 vs 短期借款图放在两张科目表（资产负债科目、变动额）之后，不提前到屏顶。无对应行时显示空态文案，不留空白图。科目行键兼容「科目」与「科目(万)」。
- 具体锚点增删清单在拿到 26H1 蓝本后 **追加本 § 子表**，并同步 plan / UI。

## 4. API 契约（概要）

> 实现时写入 `specs/api/api-contract.md` §4.5；此处为规制源。

| 方法 | 路径 | 鉴权 | 说明 |
|------|------|------|------|
| GET | `/api/competitor/editions` | view_business_dashboard | 期次列表（含是否 current、`period_label`、`has_vertical`） |
| GET | `/api/competitor/report` | 同上 | 默认 current；`?edition=` 或路径约定读指定期 |
| GET | `/api/competitor/report/meta` | 同上 | 同上 |
| GET | `/api/competitor/summary` | 同上 | 基于 **current**（首页摘要不混历史） |
| POST | `/api/competitor/admin/editions` | admin | 创建期次（id/kind/label/has_vertical） |
| POST | `/api/competitor/admin/upload` | admin | **必须**带 `edition_id`（form 字段）；写入该期目录 |
| POST | `/api/competitor/admin/current` | admin | body `{ edition_id }` 切换侧栏默认 |
| 纵向 * | 既有 vertical-* | 同上 | **一律绑定 edition**；无参时用 current；`has_vertical=false` → 404 或明确 detail |

**兼容：** 迁移期可读旧单例并映射为 `2025-annual`；新上传必须指定 edition。

**权限：** 与 1.2.3.c 相同（读 dashboard / 写 admin）。

## 5. 前端

| 项 | 约定 |
|----|------|
| 路由 | `/competitor` = current；`/competitor/e/[editionId]` = 指定期（推荐 App Router 动态段） |
| 数据 | `useCompetitorReport(editionId?)`；列表 `useCompetitorEditions()` |
| 期次切换 | 见 UI spec：页头控件，切换后加载对应 snapshot，ProgressScale 重置 |
| 空态 | 无 current / 无任何期次 → 引导财务后台；指定 edition 404 → 提示并链回 current |
| 纵向链 | 仅 `has_vertical` 时显示；href 带 edition |

## 6. 财务后台

在现有竞品上传区升级为 **期次管理 card**（可与横向/纵向分区）：

1. **列表**：edition_id、period_label、kind、是否 current、has_vertical、最近上传时间、warnings 摘要。
2. **新建期次**：填写 id（校验 `^[a-z0-9][a-z0-9_-]{0,31}$`）、kind、中文标签、has_vertical。
3. **上传横向 MD**：下拉选择 edition → `POST …/upload`（带 edition_id）。
4. **设为最新**：按钮写 `current.json`（可与上传解耦）。
5. **纵向**：仅对 `has_vertical=true` 的期次展示上传/ingest；其余隐藏或禁用说明。
6. **文案**：明确「侧栏默认 = current；历史期次在展示页切换，不会因上传另一期而删除」。

---

## 7. 纵向策略（本期默认）

| edition | has_vertical（默认） | 产品行为 |
|---------|----------------------|----------|
| `2025-annual` | `true`（迁移后） | 切到该期后可进纵向（PDF/结构化既有能力） |
| `2026-h1` | `false` | 无纵向入口；直访 vertical URL 友好说明「本期无纵向汇析」 |

若产品决定 **全局下线纵向**，将所有期次 `has_vertical=false` 并更新本表 + UI；**数据仍保留在磁盘**。

---

## 8. 验收标准

1. 迁移后仅有 2025 年报时：侧栏进入内容与迁移前一致；磁盘为 `editions/2025-annual/` + `current.json`。
2. 创建并上传 `2026-h1` 后，未切 current 前侧栏仍为 2025；设为 current 后侧栏为 26H1。
3. 页头可切回 `2025-annual`，数据与深链稳定。
4. `2026-h1` 不显示纵向入口；`2025-annual` 在切回后仍可进纵向（若迁移保留了 vertical）。
5. 上传未带 `edition_id` → 400；覆盖仅影响目标期次。
6. 非 admin 无法改 current / 上传；非 dashboard 无法 GET editions/report。
7. 单测：store 多期次、current 指针、迁移路径；API 集成：upload A → upload B → current B → GET 默认 B、`?edition=A` 仍为 A。

## 9. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 生产未跑迁移误读空库 | 启动或首次读兼容旧单例；后台显示迁移状态 |
| 管理员误切 current | UI 二次确认；current 变更写审计字段 |
| 26H1 蓝本缺主章节 | warnings + 上传诊断；必要时放宽 parser 前先改 spec |
| 纵向路径两套（根 vs editions） | store 单一 API；迁移后只认 editions 下路径 |
