### 目标业务场景（已确认）

Hermes 优先补齐的能力，与 §1.2「缺少项」一致，包括但不限于：

- **合同台账**：条款抽取、台账生成/更新、与知识库对照
- **财务流程**：流程文档生成、规则维护、与 [`/utils/process-doc`](../../frontend/app/utils/process-doc) 等能力协同（流程本身仍走 Orient-G 既有模块）
- **财务相关自动化**：跨 PDF / 表格 / 知识库 /（二期）飞书多维表与日程的编排

### Orient-G 前置能力（集成前须知晓）

| 模块 | 状态 | 对 Hermes 的影响 |
|------|------|------------------|
| 知识库 RAG + ACL | 🟡 主链路已有 | **Phase 1 直接依赖** MCP `orientg_kb_*` |
| 大 PDF / Docling | ✅ 已有 | Agent 可调现有解析任务，不假设 Hermes 自装 Docling |
| **数据解析**（1.2.2.f） | **你方尚未验收** | Hermes **不得**默认依赖 data_parse 工作流；验收后再接 MCP `orientg_data_parse_*` |
| **AI 互动工作流**（1.2.2.a） | **未充分实测** | Agent **不**替代工作空间内 workflow；并列入口，能力逐步对齐 |

### 知识库读 / 写权限（与 Hermes 对齐）

`compute_acl_scope()` 返回两套 ID（见 `backend/services/knowledge_acl.py`）：

| 集合 | 含义 | 典型规则 |
|------|------|----------|
| `allowed_*` | **可读**（检索、直读、列表） | 部门/项目公共库成员、共享到部门的 folder 内文档 |
| `writable_*` | **可写**（上传、改归属、Agent 回写） | **文档 owner**；或管理员在 **collection 维度** 授予的 `user-write-overrides` |

**你的例子**：我创建的文档共享到部门公共库 → 部门同事一般在 `allowed_doc_ids` 中**可读**，但**不在** `writable_doc_ids` 中（除非被单独授予 collection 可写）。Hermes 的 `orientg_kb_*` **写工具**必须校验 `writable_*`，读工具只校验 `allowed_*`。

**在哪里调整「写」权限？**

| 入口 | 作用 |
|------|------|
| **默认** | 上传者 = `owner` → 仅本人可写该 `ud_*` 文档 |
| **知识库页** `POST …/folders/{id}/share*` | 调整**可见/可读范围**（共享到部门/项目），**不**等于授予他人编辑 |
| **管理后台** [`/admin`](/admin) →「知识库设置」→ 按用户配置 **可读 / 可写** collection | `PUT /api/settings/kb-acl/user-write-overrides`；可写 collection 下的 doc/table 随归属可写 |

### 外部工具部署（SearXNG、Lark CLI）— 是否与 Hermes 同容器？

**不建议**全部打进 Hermes 单一镜像；推荐 **compose 多服务 + 内网 DNS**：

| 组件 | 部署方式 | 说明 |
|------|----------|------|
| **Hermes Agent** | 独立服务 `hermes-agent` | 不映射宿主机端口；`terminal.backend: docker` |
| **SearXNG** | **独立容器** `searxng` | Hermes 配置搜索端点为 `http://searxng:8080`；仅内网、引擎白名单 |
| **[larksuite/cli](https://github.com/larksuite/cli)** | **Hermes 沙盒或 sidecar 镜像**内安装 `lark` | 凭证卷 `lark-cli-config`（不进 Git）；**allowlist** 仅 finance 相关子命令 |
| **Orient-G MCP** | backend 进程 / 同 compose | KB 读写、审计、ACL；**长期飞书也可改走 MCP** 统一凭证 |

二期再开发；首版 A 可不启 SearXNG / Lark，但架构按上表预留，避免后期拆镜像迁移。

### 工具安装与权限控制（硬要求）

- Hermes **toolset 白名单**（如 `finance` profile 仅 `file`/`terminal`/`orientg` + 显式打开的 `web`/`searxng`/`lark`）。
- **禁止**生产使用 `terminal.backend: local`（宿主机全权限）。
- **禁止** Agent 会话默认安装任意 npm/pip 包；如需扩展工具须管理员改镜像或 compose。
- 浏览器/搜索/飞书：**默认关**，`HERMES_SEARXNG_ENABLED` / `HERMES_LARK_CLI_ENABLED` 环境开关。
- 所有 KB 写、飞书写操作：**经 Orient-G MCP** 或 **审计过的包装命令**，并记 `channel: hermes.*`。

### 页面集成后，Hermes「命令」能否生效？

| 用户看到的 | 实际执行 |
|------------|----------|
| 在 `/agent` 输入自然语言 | backend 调 Hermes **HTTP API**（见 §5.2 修订），非浏览器跑 CLI |
| 执行步骤里的 `lark …`、`search …` | Hermes 在**沙盒内**调用已安装工具；结果以 `tool_calls` 回传页面 |
| 用户**不需要**也不会输入 `hermes` / `lark` 子命令 | 与「宿主机 Hermes CLI 试用」是两条线 |

## 1. 背景与动机

### 1.1 Hermes Agent 是什么

Hermes Agent（[NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent)）是一个**自改进 AI Agent**，区别于普通聊天机器人：

- **学习循环**：从经验创建 skills，使用中自动改进
- **记忆系统**：跨会话持久记忆 + 用户画像（Honcho 方言建模）
- **工具生态**：61 个工具 / 52 个 toolsets（终端、浏览器、文件、MCP 等）
- **多平台**：CLI、Telegram、Discord、Slack、WhatsApp、Signal、Email 等
- **终端后端**：本地、Docker、SSH、Modal、Daytona、Singularity、Vercel Sandbox 等 7 种
- **技能市场**：兼容 [agentskills.io](https://agentskills.io) 开放标准

### 1.2 为什么考虑引入

当前 Orient-G 的 `/ai-interaction` 已具备：
- 知识库 RAG 检索（collections/tables/folders）
- 工作流系统（workflow + skills + tools + prompts）
- 数据解析（Excel → 看板/图表）
- 大 PDF 处理（Docling → 知识库）

**但缺少**：
- **复杂任务自动化**：例如"把这份合同的财务条款提取出来，生成台账，并对比上个月的异常"
- **跨工具编排**：需要串联"PDF 解析 → 数据提取 → 计算 → 生成报表 → 存入知识库"
- **自主学习沉淀**：同一类任务重复执行时，自动优化执行路径

Hermes Agent 的核心价值恰好填补这些空白。

### 1.3 关键约束

- **受众**：财务部门同事，非技术人员，学习成本敏感
- **环境**：仅内网，Ubuntu Server + Docker，已部署 Orient-G
- **安全**：严格防数据外泄，所有 AI 处理必须在本地/内网完成
- **稳定**：生产环境，不能因引入新组件降低现有服务稳定性

## 2. 方案总览：不是替代，是增强

### 2.1 核心原则

**不把 Hermes 当作聊天替代品，而是作为"能力增强层"**：

```
用户 → Orient-G AI 互动页（现有 UI，保持不变）
    ↓
    ├─→ 普通问答 → 现有 /api/ai-interaction/chat（RAG + 工作流）
    │
    └─→ 【新增】"启用高级 Agent" → Hermes Agent（Docker 隔离）
            ↓
            ├─→ 复杂任务分解与执行
            ├─→ 多工具编排（文件+终端+浏览器+MCP）
            ├─→ 自主 skill 创建与复用
            └─→ 结果返回 → AI 互动页展示（保持统一体验）
```

### 2.2 为什么这样设计

| 维度 | 如果完全替代现有 AI 互动 | 如果作为增强层（本方案） |
|------|------------------------|------------------------|
| **用户学习成本** | 高：需要理解 Hermes 的 CLI/命令 | 低：保持现有 Web 界面，零学习成本 |
| **现有投资** | 浪费：RAG、KB、工作流需重写 | 保留：现有系统继续运作 |
| **安全边界** | 模糊：Hermes 终端权限难以控制 | 清晰：Docker 隔离，显式授权 |
| **渐进引入** | 不可行：一次性替换风险高 | 可行：逐个场景验证价值 |
| **财务同事接受度** | 低：CLI 对非技术人员不友好 | 高：Web 页面一键切换 |

```
│  └─────────────────────────────────────────────────┘   │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 3.2 网络与通信

```
Orient-G backend:8000  ←──HTTP──→  Hermes Agent（内部 API）
        ↑                              ↑
        │                              │
   用户浏览器                      Docker 内部网络
   （AI 互动页）                    （bridge/隔离）
```

**关键设计**：
- Hermes Agent 不直接暴露端口到宿主机（仅内网 Docker 网络可达）
- Orient-G backend 作为唯一入口，所有请求必须经过后端路由
- Hermes 的终端后端强制使用 Docker 隔离（禁止 local/ssh 模式）

- **标准模式**：现有 `/api/ai-interaction/chat`，RAG + 工作流
- **高级 Agent 模式**：新增 `/api/hermes/chat`，调用 Hermes Agent

### 4.2 透明化展示（可选，用于排查）

当使用高级 Agent 模式时，在消息气泡下方展示**可折叠的执行日志**：

```
AI：已完成合同台账生成，共提取 12 条财务条款...

[▼ 查看执行过程（点击展开）]
  1. 📄 读取文件：contract_2026.pdf（Docling 解析）
  2. 🔍 提取条款：财务相关章节（3 处）
  3. 🧮 计算指标：金额汇总、同比...
  4. 📝 生成台账：contract_ledger_2026.xlsx
  5. 💾 存入知识库：合同管理/2026
```

**对财务同事**：默认折叠，不影响阅读；对技术人员：展开可见详细执行链。

### 4.3 为什么 CLI 不适合本场景

Hermes Agent 原生提供 CLI（`hermes`）和 TUI（`hermes --tui`），但：

| 问题 | 说明 |
|------|------|
| **学习成本** | 需要记住 slash 命令（`/model`, `/tools`, `/skills`） |
| **环境依赖** | 需要 SSH 到服务器或本地终端 |
| **权限风险** | CLI 默认有终端执行权限，误操作风险高 |
| **会话隔离** | CLI 会话存储在服务器本地，与 Web 会话不互通 |
| **不符合习惯** | 财务同事习惯 Web 页面操作，非命令行 |

**结论**：Web UI 封装是唯一可行的方式。

## 5. 后端集成方案

### 5.1 新增路由：`POST /api/hermes/chat`

**请求体**：

```json
{
  "messages": [
    {"role": "user", "content": "帮我把这份合同的财务条款提取出来，生成台账"}
  ],
  "kb_scope": {
    "selected_collection_ids": ["c_contracts"],
    "selected_folder_ids": ["f_2026"]
  },
  "attachments": [
    {"doc_id": "ud_contract_001", "name": "contract_2026.pdf"}
  ],
  "session_id": "s_xxx",
  "profile": "finance"  // Hermes profile 隔离
}
```

**响应体**：

```json
{
  "reply": "已完成合同台账生成...",
  "citations": [...],
  "tool_calls": [
    {"step": 1, "tool": "docling.parse", "status": "ok", "output": "..."},
    {"step": 2, "tool": "extract.clauses", "status": "ok", "output": "..."},
    {"step": 3, "tool": "generate.ledger", "status": "ok", "output": "..."}
  ],
  "artifacts": [
    {"type": "file", "name": "contract_ledger_2026.xlsx", "url": "/api/artifacts/..."}
  ],
  "hermes_session_id": "h_xxx"  // 用于续对话
}
```

### 5.2 Hermes Agent 调用方式（v2 修订：一步到位、避免二次迁移）

> **结论：生产首版采用方案 B（内网 HTTP）**，不再推荐 `docker exec` + `hermes run` 作为主线。  
> 宿主机 CLI 仅用于运维/Phase 0 试用；`/agent` 页面只对话 backend。

| 方案 | 评价 |
|------|------|
| **A. `docker exec` + subprocess** | 难做流式输出、会话续聊、统一超时与取消；升级 Hermes 易碎；**仅作应急** |
| **B. 内网 HTTP API（推荐）** | `hermes-agent` 常驻容器，监听 `orientg_internal` 网络；backend `POST http://hermes-agent:PORT/...`；支持 JSON/SSE、与页面 `tool_calls` 对齐 |
| **C. 同进程嵌入 Hermes** | 耦合过重，**不采用** |

**推荐 compose 形态（与 Orient-G 同文件或 overlay）：**

```yaml
hermes-agent:
  image: hermes-agent:pin-xxx          # 版本锁定
  networks: [orientg_internal]
  env_file: .env.hermes                 # LLM_BASE_URL、toolset 白名单；二期 FEISHU/LARK 凭证
  volumes:
    - hermes_state:/root/.hermes
    - ./secrets/lark-cli:/root/.lark:ro # 二期：larksuite/cli 配置
  # 不 ports 到宿主机
  mem_limit: 8g
```

**backend 调用约定（实现时对齐 `specs/api` 扩展）：**

- `POST /api/agent/chat` → `hermes_client.run(...)` → `http://hermes-agent:8787/v1/agent/run`（端口以 Hermes 版本为准）
- 请求携带：`messages`、`kb_scope`、`user_token` 摘要、`allowed_toolsets`、`orientg_mcp_endpoint`（stdio 由 Hermes 侧 spawn 或 sidecar）
- 响应：`reply`、`tool_calls[]`、`hermes_session_id`；**SSE 流**（`stream: true` + `stream_tool_progress: true`）
- Gateway 自定义事件 `event: hermes.tool.progress`（toolCallId / emoji / label / status）由 `hermes_client.HermesSseParser` 解析并透传为 Orient-G SSE `type: tool_progress`；页面「执行过程」展示，**不**写入助手正文（与 Open WebUI 一致）。操作说明见 [`docs/hermes.md`](../../docs/hermes.md) §5。

**安全：** Hermes HTTP **仅** Docker 内网可达；Caddy/公网不路由；mTLS 或 shared secret 可选加固。

### 5.3 安全与隔离

| 层面 | 措施 |
|------|------|
| **容器隔离** | Hermes 运行在独立 Docker 容器，与 Orient-G 服务隔离 |
| **终端隔离** | Hermes `terminal.backend` 强制设为 `docker`，禁止 local/ssh |
| **网络隔离** | Hermes 容器不暴露端口，仅通过 Docker 内部网络通信 |
| **文件隔离** | Hermes 只能访问挂载的特定目录（uploads、tmp），禁止访问系统目录 |
| **权限控制** | Orient-G backend 作为网关，所有请求必须经过鉴权 |
| **超时熔断** | 单次调用 5 分钟超时，防止长时间占用 |

## 6. 数据流与状态管理

### 6.1 会话隔离

| 系统 | 会话存储 | 说明 |
|------|----------|------|
| Orient-G | localStorage（前端）+ 后端无状态 | 现有模式 |
| Hermes | SQLite（`~/.hermes/state.db`） | 独立存储 |

**桥接策略**：
- Orient-G 的 `session_id` 映射到 Hermes 的 `profile` + `hermes_session_id`
- 每次调用 Hermes 时，传入 `profile` 和可选的 `hermes_session_id`（续对话）
- Hermes 的会话历史不直接暴露给前端，由后端路由管理

### 6.2 知识库互通

```
Orient-G KB（PostgreSQL + 向量库）
    ↑                              ↓
    │  1. 用户选择范围（collections/folders）
    │  2. Orient-G 后端将范围转为 Hermes context
    │  3. Hermes 执行任务时，通过 MCP 或 API 查询 KB
    │  4. 结果返回 Orient-G 展示
    │                              ↑
Hermes Agent（通过 MCP 或 API 访问 KB）
```

**实现**：将 Orient-G 的知识库查询封装为 Hermes 的 MCP Server 或 Tool。

## 7. 实施路线图

### Phase 0：验证（1-2 周）

**目标**：验证 Hermes Agent 对财务场景的价值

1. **部署 Hermes**（独立 Docker，内网）
   ```bash
   # /opt/hermes-agent/
   git clone https://github.com/NousResearch/hermes-agent.git
   cd hermes-agent
   # 构建 Docker 镜像
   docker build -t hermes-agent:local .

   docker run -d --name hermes-agent \
     --network orient-g_default \
     -v /opt/orient-g/uploads:/shared/uploads:ro \
     -e HERMES_PROFILE=finance \
     hermes-agent:local
   ```

2. **团队内部试用 CLI**
   - 财务同事试用 3-5 个典型任务
   - 收集反馈：哪些任务 Hermes 比现有系统更高效

3. **评估价值**
   - 如果价值不明确 → 停止，保持现有系统
   - 如果价值明确 → 进入 Phase 1

### Phase 1：MCP 桥接（2-3 周）

**目标**：让 Hermes 能调用 Orient-G 的能力

1. **开发 Orient-G MCP Server**
   - 暴露知识库查询、文件上传、数据解析等能力
   - 作为 Hermes 的 MCP Server 注册

2. **开发 Hermes Tool**
   - 将 Orient-G 的能力封装为 Hermes 的 Tool

3. **内部验证**
   - 在 Hermes CLI 中测试调用 Orient-G 能力
   - 验证任务链："上传 PDF → 解析 → 存入 KB → 生成报表"

### Phase 2：Web UI 集成（3-4 周）

**目标**：在 AI 互动页添加"高级 Agent"模式

1. **后端开发**
   - 新增 `POST /api/hermes/chat` 路由
   - 实现 Hermes 调用封装（subprocess 或 HTTP）
   - 会话映射与管理

2. **前端开发**
   - 添加模式切换开关
   - 执行日志展示（可折叠）
   - 产物下载（生成的文件）

3. **安全加固**
   - Docker 隔离验证
   - 超时与熔断测试
   - 权限边界确认

### Phase 3：优化与扩展（持续）

**目标**：根据使用反馈优化

1. **Skill 沉淀**
   - 将高频任务沉淀为 Hermes Skills
   - 与 Orient-G 的 agent_skills 互通

2. **性能优化**
   - Hermes 调用改为异步（WebSocket 或 SSE）
   - 长任务支持后台执行 + 通知

3. **更多场景**
   - 自动化报表生成（Cron）
   - 跨平台通知（企业微信/钉钉）

## 8. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| **Hermes 学习曲线** | 开发团队需要理解 Hermes 架构 | Phase 0 充分验证，必要时请外部支持 |
| **性能问题** | Hermes Agent 循环可能耗时较长 | 超时熔断 + 异步执行 + 进度反馈 |
| **安全边界** | Hermes 工具执行可能越权 | 强制 Docker 隔离 + 最小权限原则 |
| **稳定性** | 新组件可能拖垮现有服务 | 独立容器 + 健康检查 + 快速回滚 |
| **用户接受度** | 财务同事可能不信任"黑盒"Agent | 透明化执行日志 + 人工确认关键步骤 |
| **维护成本** | Hermes 版本更新可能破坏集成 | 锁定版本 + 充分测试后再升级 |

   - [ ] Docker 容器（推荐）
